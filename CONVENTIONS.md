# Conventions

How every namespace and skill in this repo is structured. Followed by
`y7vim/` already; apply the same shape to whatever gets added next.

## Repo layout

```
y7-skills/
├── README.md              — what this repo is, list of namespaces
├── CLAUDE.md               — rules for Claude Code working in this repo
├── CONVENTIONS.md          — this file
└── <namespace>/            — one toolchain area, e.g. y7vim/
    ├── README.md           — what this namespace covers
    ├── sources.yml          — pinned upstream versions, see below
    ├── scripts/             — shared scripts across the namespace's skills
    ├── docs/
    │   ├── <topic>.md             — how the pieces in this namespace fit together
    │   └── problems-and-workarounds.md   — running incident log, see below
    └── skills/
        └── <namespace>-<capability>/     — one skill, e.g. y7vim-claudecode
            ├── SKILL.md
            ├── scripts/      — install-*.sh, verify.sh, idempotent
            └── references/   — generated-where-possible, keymap/command tables
```

## Skill naming

`<namespace>-<capability>`, lowercase, hyphenated — e.g. `y7vim-claudecode`,
`y7vim-lazyclaude`, `y7vim-autodetect`. The namespace prefix keeps names
unambiguous once more namespaces exist; `npx skills add` resolves by this
exact name.

## SKILL.md

Plain frontmatter, no business/telemetry runtime layer:

```yaml
---
name: <namespace>-<capability>
description: "<one sentence, quoted — an unquoted colon inside breaks some skill-install CLIs>"
version: 1.0.0
---
```

Body: what it installs, what it needs first, an install sequence calling
its own `scripts/`, a keymap/command table (or link to `references/`), and
a "Sources used" section linking every upstream project it wraps.

## Scripts

- Every install script is **idempotent** — safe to re-run, checks before
  acting (`command -v`, version comparison, file existence) rather than
  assuming a clean slate.
- Every install script is **additive, never destructive** — merges into
  existing config rather than overwriting it, and says so in a comment at
  the top if it touches a file outside its own skill folder.
- `verify.sh` in each skill either filters the namespace's shared test
  suite, or — when a script can run against a throwaway fixture instead of
  the user's real config — tests against a `mktemp -d` fixture so it never
  touches real state.
- `set -euo pipefail` at the top of every script. Any command inside a loop
  that's allowed to legitimately find nothing (e.g. `grep` with no match)
  gets `|| true` — otherwise `set -e` silently kills that iteration. Hit
  this twice already; see `y7vim/docs/problems-and-workarounds.md`.

## references/

Prefer **generated** reference files over hand-written ones whenever the
source of truth is an upstream project's own source code (e.g.
`y7vim-autodetect/references/extra-root-markers.md`, generated by
`gen-markers-reference.sh` from LazyVim's own extras). A generated file
can be regenerated after an upstream upgrade instead of silently going
stale. Say so in the file's own header.

## sources.yml

One per namespace. Every entry is a version actually installed and tested
against during development — never a guess. Each namespace also gets a
`scripts/check-updates.sh` that diffs against upstream and only reports;
nothing in this repo auto-bumps a pinned version.

## docs/problems-and-workarounds.md

One per namespace, append-only in spirit (never delete a past entry,
even if later irrelevant — mark it superseded instead). Entry format:

```md
## <short title>
**Symptom:** what you saw
**Cause:** what was actually wrong (verified, not guessed)
**Fix:** the exact command/change
**How we caught it:** which test or check surfaced it
```

Every entry must come from something that actually happened while
building or testing — not a hypothetical "this could go wrong."

## Testing

Every namespace has one shared `scripts/test-config.sh` or equivalent,
and every skill's `verify.sh` is a thin filter over it (or a standalone
fixture test). Running the full suite and getting a clean pass is the bar
for "done," not "the script looked right when I wrote it" — this repo has
already caught real bugs (a `--noplugin` flag that disabled the very
plugin under test, `set -e` dropping loop iterations) that only surfaced
by actually running things.
